# acmed v0.4.0 Release Notes

## Summary

`v0.4.0` is a minor release because the changes since `v0.3.5` include optional
HTTPS listeners and listener-certificate bootstrapping. It also fixes native
ACME issuance for EC clients such as Caddy without removing RSA CSR support.

## Added

- Optional additional HTTPS listeners configured through `server.extra_listeners`.
- Startup listener-certificate bootstrapping through `server.listener_certificate`,
  using the existing policy and issuer configuration. Bootstrap applies the
  configured renewal window at startup; it does not introduce a background
  listener-certificate renewal scheduler.

## Fixed

- `acme_sh` now selects RSA or ECC installation based on the finalized CSR key.
  EC requests use `--ecc`, while RSA requests retain their existing lineage.
- Both the standalone certificate and full-chain leaf must match the client CSR
  public key before issuance is reported as successful. This blocks stale
  certificate output, including different keys with the same algorithm.
- Malformed or unsupported CSR keys fail before issuer subprocess execution.
- JSON responses have a default Content-Type, and worker claims include the
  `issuing` state.

## Compatibility

Existing configurations remain supported; HTTPS listener settings are optional.
No ACME wire schema or new authorization grants are introduced. Malformed CSRs
and mismatched issuer output now fail rather than appearing to succeed. The
acme.sh client-CSR adapter supports RSA and EC keys.

Client certificate private keys remain on the client. DNS issuer credentials
remain on the issuance service. This release does not change configured client
challenge policy; HTTP-01/TLS-ALPN-01 support alone does not enable strict
validation when a deployment has selected `trusted_bypass`.

## Validation

The complete core suite passed locally: 66 tests, including real RSA/EC public
artifacts and mismatched-certificate regressions. An issuer-only deployment of
the fix completed a native Caddy order; its CSR, certificate and full-chain leaf
public keys matched, and the application returned HTTP 200 with normal HTTPS
verification. That maintenance deployment is distinct from the full release
image built by the release pipeline.
